### **背景**

![](/雪花算法/log.png)

雪花算法的机器标识是相同的, 导致相同毫秒时生成id冲突.



### **雪花算法**

1. 第一位0, 表示正数
2. 41位时间戳, 因为只有41位, 所以是一个相对起始时间的偏移值, 因此起始时间不能修改
3. 10位机器标识, 分为5位datacenterId, 5位workerId
4. 12位序列号, 同一毫秒内的自增序列号



### **mybatis**

`com.baomidou.mybatisplus.core.toolkit.Sequence`目前使用的是该类生成id

```
protected long getMaxWorkerId(long datacenterId, long maxWorkerId) {
    StringBuilder mpid = new StringBuilder();
    mpid.append(datacenterId);
    String name = ManagementFactory.getRuntimeMXBean().getName();
    if (StringUtils.isNotBlank(name)) {
        /*
         * GET jvmPid
         */
        mpid.append(name.split(StringPool.AT)[0]);
    }
    /*
     * MAC + PID 的 hashcode 获取16个低位
     */
    return (mpid.toString().hashCode() & 0xffff) % (maxWorkerId + 1);
}
```

生成workerId时只用了datacenterId和进程id, 但是在容器中, 进程id都是1, 所以只要datacenterId冲突了, 那么workerId就是冲突的. 等于原来是1/1024的概率冲突, 现在只有1/32的概率冲突.



### hutool

`cn.hutool.core.lang.Snowflake`切换成hutool的雪花算法实现. 阿里云的机器可能会有10ms的时钟回拨, hutool的实现容忍可以配置大于10ms

1. 两者起始时间一致
2. hutool允许的时钟回拨可配置, mybatisplus的固定为5毫秒
3. mybatisplus时钟回拨策略是wait, hutool的是切换到当前缓存时间戳



### **leaf**

[Leaf——美团点评分布式ID生成系统](https://tech.meituan.com/2017/04/21/mt-leaf.html),文档中也介绍了其他一些方案

1. 步长获取
2. 双buffer, 在耗尽前提前获取
3. 高可用, 个人感觉数据库不可用了也不用担心id不能生成了
4. leaf-snowflake, 使用zk保证workerId不冲突, 当然更复杂, 有上报什么的



### **面试题**



#### Q1: 为什么需要分布式 ID？本地自增主键不行吗？

单机场景下数据库自增主键够用, 但分布式场景下有问题:

1. 分库分表后, 各个库的本地自增主键会重复
2. 数据迁移、合并时主键冲突
3. 业务往往需要 ID 在生成时就唯一, 而不是等落库才知道, 比如订单号在创建订单前就要确定

所以需要一个全局唯一的 ID 生成方案。



#### Q2: 雪花算法的 64 位结构是怎样的？每部分的作用？

```
0 | 41位时间戳 | 5位datacenterId | 5位workerId | 12位序列号
```

- 1 位符号位, 固定为 0, 保证是正数
- 41 位时间戳, 毫秒级, 是相对起始时间的偏移值, 不是绝对时间
- 10 位机器标识, 理论支持 1024 个节点
- 12 位序列号, 同一毫秒内的自增序列, 单节点单毫秒最多 4096 个 ID



#### Q3: 41 位时间戳能用多久？起始时间能改吗？

41 位最大值约 69.7 年（2^41 / 1000 / 60 / 60 / 24 / 365）。

起始时间不能随便改, 因为时间戳是相对偏移值。如果改了起始时间, 已经生成的 ID 和新生成的 ID 的相对关系会错乱, 可能出现 ID 不再递增甚至重复。所以设计时要选一个合理的起始时间（比如系统上线时间）, 留足几十年的余量。



#### Q4: 同一毫秒序列号用完了怎么办？

12 位序列号最多 4096 个, 单节点单毫秒超过 4096 个 ID 会溢出。

通常的处理方式是: 等到下一毫秒再生成, 也就是当前毫秒内的请求会短暂等待。实际业务中单节点单毫秒生成 4096 个 ID 已经很高了, 很少触发。如果真有这种压力, 说明该考虑分摊到更多节点了。



#### Q5: 时钟回拨问题是什么？怎么解决？

服务器时钟可能因为 NTP 同步等原因往回拨, 导致时间戳比之前小, 可能生成重复 ID。

常见解决方案:

1. 回拨时间小（如几毫秒）: 等待, 等时钟追上来再生成, mybatis-plus 默认 5ms 内 wait
2. 回拨时间较大: 用上次记录的最大时间戳兜底, 而不是用当前系统时间, hutool 就是这个策略
3. 扩展位: 拿出几位做扩展位, 时钟回拨时启用, 但会牺牲部分机器位或序列位
4. 不容忍直接报错: 简单粗暴, 适合回拨概率极低的场景



#### Q6: workerId 怎么分配？如何保证不冲突？

这是雪花算法落地最关键的问题。workerId 必须全局唯一, 否则会产生重复 ID。

常见方案:

1. 配置文件写死: 简单, 但运维成本高, 扩容时容易配错
2. 数据库自增分配: 每个节点启动时去数据库取一个, 简单可靠, 但依赖数据库
3. ZooKeeper/ETCD 分配: leaf-snowflake 的做法, 启动时申请, 挂了能回收, 但依赖中间件
4. MAC + PID 的 hashcode: mybatis-plus 的做法, 不依赖外部, 但容器内 PID 都是 1, 容易冲突, 概率从 1/1024 变成 1/32
5. Redis 分配: 用 INCR 分配 workerId, 也行, 但又多一个依赖



#### Q7: 雪花算法的优缺点？

优点:

1. 生成速度快, 本地计算, 无需网络开销
2. 趋势递增, 基于时间戳, 对数据库索引友好
3. 不依赖外部存储, 无单点问题
4. 64 位, 可作为 long 存储, 占用空间小

缺点:

1. 依赖机器时钟, 有时钟回拨风险
2. workerId 分配需要额外机制, 容器化环境下尤其麻烦
3. 起始时间一旦确定不能改, 有 69 年寿命限制
4. 不是严格单调递增, 只是趋势递增（同一毫秒内序列号递增, 但跨节点的先后顺序无法保证）



#### Q8: 雪花算法和 UUID 的区别？各自适合什么场景？

UUID 有多个版本, 不能一概而论:

- UUID v1: 基于时间戳 + MAC 地址, 时间有序, 但暴露 MAC 有隐私问题
- UUID v4: 纯随机, 无序, 最常用但做主键性能差
- UUID v6: 时间戳重新排序到高位, 比 v1 更利于索引（RFC 9562）
- UUID v7: 前 48 位是毫秒级时间戳, 后面随机, 趋势递增, 适合做数据库主键（RFC 9562, 2024 年标准化）

核心区别:

1. 长度: UUID 128 位, 雪花 64 位, 数据库存储和索引开销差一倍
2. 递增性: v4 无序做主键会频繁页分裂; v7 趋势递增, 和雪花一样适合做主键
3. 唯一性保证: UUID 概率唯一（碰撞概率极低但理论存在）, 雪花算法在 workerId 唯一且时钟不回拨的前提下严格唯一
4. 依赖: UUID 完全无依赖, 不需要 workerId 分配, 不依赖时钟同步精度（v7 也只需毫秒级）; 雪花需要解决 workerId 和时钟回拨
5. 适用场景: v4 适合做 traceId、文件名; v7 和雪花都适合做数据库主键, v7 更简单（无需 workerId）, 雪花更紧凑（64 位）



#### Q9: 常见的分布式 ID 方案有哪些？怎么选？

1. UUID v4: 简单无依赖, 但无序、太长, 不适合做主键
2. UUID v7: 趋势递增、无依赖, 适合做主键, 但 128 位比雪花长一倍
3. 数据库自增: 简单, 但有性能瓶颈和单点问题, 分库分表后无法用
4. 数据库号段模式（如 leaf-segment）: 一次取一批, 性能高, 趋势递增, 但依赖数据库, ID 不连续
5. 雪花算法: 本地生成、高性能、趋势递增, 但有 workerId 和时钟回拨问题
6. Redis INCR: 简单, 性能高, 但依赖 Redis, 持久化策略不当可能重复
7. TinyID（滴滴）: 号段模式, 支持多 DB, 类似 leaf-segment

选型考虑: 不想搞 workerId 分配又要趋势递增 → UUID v7; 追求紧凑和高性能、能搞定 workerId → 雪花算法; 对连续性无要求、要简单 → 号段模式



#### Q10: 雪花算法如何保证趋势递增？能保证严格递增吗？

趋势递增靠的是时间戳在高位, 时间往后走, ID 整体递增。同一毫秒内序列号自增, 也保证同节点同毫秒内递增。

但严格递增做不到:

1. 多节点之间, A 节点先生成的 ID 可能比 B 节点后生成的 ID 大（时间戳相同但 workerId 不同, 或时间戳不同但网络延迟导致落库顺序乱）
2. 时钟回拨时, 会出现时间戳倒退

对数据库索引来说, 趋势递增就够了, 不需要严格递增。严格递增需要单点生成, 会成为瓶颈。
